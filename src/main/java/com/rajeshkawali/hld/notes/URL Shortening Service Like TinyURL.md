# Design URL Shortening Service Like TinyURL

## 1. Problem

Convert a long URL into a short URL.

Example:

Long URL:
https://example.com/products/12345

Short URL:
https://tiny.url/aB7xK2

When the user opens the short URL, the service finds the original URL and redirects the user.

---

## 2. Main Requirements

### Functional

1. Create a short URL
2. Redirect short URL → original URL
3. Optional:
   - URL expiration
   - Custom short URL
   - Click analytics

### Non-Functional

- Low latency
- High availability
- Scalable
- Unique short codes
- Durable storage

# 5. Short Code Generation

## Option 1: Auto-Increment ID + Base62 ⭐ Recommended

Generate a unique ID:

100001

Convert it to Base62:

100001 → "q3X9"

Final:

tiny.url/q3X9


### Base62

Characters:

0-9
a-z
A-Z

Total = 62 characters.

### Advantages

- Simple
- Fast
- Short URL
- No collision if ID is unique
- Easy to implement

### Disadvantages

- Predictable IDs
- Sequential IDs may reveal approximate URL creation volume
- Central DB sequence can become a bottleneck at very large scale


---

# 6. Option 2: Random String

Generate:

random() → aB7xK2

Check database:

Does aB7xK2 already exist?

If YES → generate again
If NO → store it


### Advantages

- Harder to predict
- No sequential IDs
- Can generate independently

### Disadvantages

- Possible collisions
- Need database lookup/check
- Collision probability increases as data grows


---

# 7. Option 3: UUID + Encoding

Generate:

UUID
  ↓
Encode
  ↓
Short Code


### Advantages

- Globally unique
- Can be generated by multiple servers
- No central sequence required

### Disadvantages

- UUID is long
- More complex
- Not necessary for a simple URL shortener


---

# 8. Option 4: Distributed ID Generator

Use a Snowflake-style ID generator.

Application
    ↓
Distributed ID Generator
    ↓
Unique ID
    ↓
Base62
    ↓
Short Code


### Advantages

- High throughput
- Unique across multiple servers
- No single DB sequence bottleneck
- Good for large-scale systems

### Disadvantages

- More complex
- Requires distributed ID-generation logic
- IDs can still be somewhat predictable


---

# 9. ID Generation Comparison

| Method | Advantages | Disadvantages |
|---|---|---|
| Auto ID + Base62 | Simple, fast, no collision | Predictable |
| Random String | Unpredictable | Collision checking |
| UUID + Encoding | Globally unique | Long/complex |
| Distributed ID + Base62 | Highly scalable | More complex |

### Interview Choice

Start with:

Auto-increment / unique ID + Base62

At very large scale:

Distributed ID Generator + Base62

# 10. Database Storage Options

## Option 1: SQL Database ⭐ Good Starting Point

Example table:

URL

- id
- short_code
- long_url
- created_at
- expires_at
- user_id

Example:

id = 1001
short_code = aB7xK2
long_url = https://example.com/product/123


### Advantages

- Simple
- Strong consistency
- Transactions
- Unique constraints
- Easy indexing
- Mature technology

### Disadvantages

- Horizontal scaling is harder
- Very large datasets may need sharding
- High traffic can overload one DB


---

# 11. Option 2: NoSQL Database

Examples:

- DynamoDB
- Cassandra
- MongoDB

Store:

short_code → long_url

Example:

aB7xK2 → https://example.com/product/123


### Advantages

- Easy horizontal scaling
- High read/write throughput
- Good for very large datasets

### Disadvantages

- More complex consistency model depending on DB
- Limited complex queries
- Additional design/operational complexity


---

# 12. Option 3: Key-Value Database

TinyURL is basically:

short_code → long_url

So a key-value database is a natural fit.

Example:

aB7xK2 → https://example.com/product/123


### Advantages

- Very fast lookup
- Simple
- Easy to scale

### Disadvantages

- Limited query capabilities
- Not ideal for complex relational queries
- May need another database for analytics/user data


---

# 13. Redis

Redis should normally be used as a CACHE, not the primary source of truth.

Database = Source of Truth
Redis    = Cache


Example:

Redis:

aB7xK2 → https://example.com/product/123


### Advantages

- Very fast
- Reduces DB load
- Low latency
- Good for frequently accessed URLs

### Disadvantages

- Memory is expensive
- Data can be evicted
- Cache failure should not cause data loss


---

# 14. Database Comparison

| Storage | Advantages | Disadvantages | Use |
|---|---|---|---|
| SQL | Simple, consistent, indexed | Harder to scale horizontally | ⭐ Starting point |
| NoSQL | Highly scalable | More complex | Very large scale |
| Key-Value | Very fast lookup | Limited queries | URL mapping |
| Redis | Extremely fast | Cache, not durable source | ⭐ Cache |

# 17. Why Redis?

URL shorteners are generally READ-HEAVY.

Example:

1 URL creation
      ↓
100+ redirects


Without Redis:

100 requests
     ↓
Database


With Redis:

100 requests
     ↓
Redis
     ↓
Most requests served from cache


Benefits:

- Lower response time
- Lower DB load
- Higher throughput

# 18. Important Database Index

The most important lookup is:

short_code → long_url

Therefore:

UNIQUE INDEX(short_code)


Example:

short_code = aB7xK2

Database can quickly find:

aB7xK2 → https://example.com/product/123

# 21. Hot URL Problem

Suppose one URL suddenly receives millions of requests.

Example:

tiny.url/abc123
      ↓
10 million requests


This is called a HOT KEY.

Solution:

- Redis caching
- Local application cache
- Redis replication
- CDN/edge caching where appropriate
- Request coalescing if needed

# 24. 301 vs 302 Redirect

### 301

Permanent redirect.

Browser/CDN may cache it.

### 302

Temporary redirect.

Gives the server more control over redirect behavior.

### Interview Answer

Use 302 initially unless the product guarantees that the destination is permanently fixed.

# 26. Interview Follow-Up Questions

### Q: How do you generate the short code?

Answer:

Use a unique ID and encode it using Base62.


### Q: Why Base62?

Answer:

Base62 uses 62 characters, so large numbers can be represented using short strings.


### Q: How do you prevent collision?

Answer:

Use a globally unique ID + Base62, or if using random strings, enforce a unique database constraint and retry on collision.


### Q: Why Redis?

Answer:

URL shorteners are read-heavy, so Redis reduces database reads and improves response time.


### Q: What if Redis goes down?

Answer:

Fall back to the database. Redis is a cache; the database remains the source of truth.


### Q: How do you scale the application?

Answer:

Use stateless application servers behind a load balancer and scale horizontally.


### Q: When would you use sharding?

Answer:

Only when a single database cannot handle the required data size or traffic after simpler optimizations such as indexing, caching, replicas, and scaling.
